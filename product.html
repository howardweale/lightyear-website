The Verdict Engine

An independent judge for modernization. It runs the old system and the new one on the same inputs, compares every field, and signs a verdict your auditor can replay. It is a fixed program, tested before use. It is not an AI model.

What the engine does

It compares the two systems field by field

Every record, every field, aligned by key and judged against your equivalence policy. A one-cent difference halts the run and names the field that caused it.

The verdict names the field and the cause, not just pass or fail.

The answer most tools cannot give

Three verdicts, not two

Every comparison tool returns pass or fail. That is the problem. A tool with only two answers has to pick one even when it has verified nothing — and it will pick pass, because nothing went wrong.

VerdictWhat it meansExit
equivalentBoth systems produced the same result, within the policy you approved.0
divergentThey differ. The receipt names the field and the cause.1
indeterminateWe could not verify this, and we will not pretend otherwise. Nothing comparable was produced, or the construct is outside what we can decide.2

The third verdict is the one no other tool returns, and it is the reason the first two can be trusted. An engine that never says indeterminate is not more capable. It is less honest.

What we test for

The dangerous answer is not a wrong one. It is a confident empty one.

A tool that reports success having checked nothing looks exactly like a tool that works. It ships, and you find out when the numbers stop reconciling. We attack our own Verdict Engine on every build to make sure it cannot do that.

What it does without asking you

It does the safe work itself. It stops before anything else.

Every verdict produces work with a named owner. Six kinds of work run unattended, because none of them can turn a difference into an acceptance: re-run the comparison, escalate to a deeper lane, extend the corpus, re-parse with a wider grammar, widen observation, and apply a normalization your team already approved.

Proposing a new normalization, classifying a change as intentional, promoting a claim — these stop and ask. Not by convention. A configuration that would let them run unattended is rejected by the software. Authority can be reduced. It cannot be increased.

exit 2

Exit 0 lets the release proceed. Exit 1 halts it on a divergence. Exit 2 halts it because something could not be verified — the exit code most tools do not have.

Wire it in once and verification stops being a phase you schedule. It becomes a property of the pipeline, like your build or your tests: every change is measured against the system it replaces, the evidence accumulates commit by commit, and the release either carries proof or it does not ship.

Where the evidence comes from

Sign-off stops being an event at the end

Today a modernization programme verifies at milestones. Someone runs a comparison, writes a report, and a committee reads it weeks later — by which point the code has moved on and the evidence describes a system that no longer exists.

In a pipeline, every commit carries its own evidence. Sign-off becomes an accumulated record rather than a meeting, and the question at go-live changes from “can someone check this?” to “read what we already have.”

We run it on ourselves this way. Every push to our own repository runs the engine in GitHub Actions — the same command, the same exit codes, on public code you can read. It is one step in a workflow file, not an integration project.

Three ways to run it, and no difference between them. An engineer at a terminal, a step in the build you already have, or the AI assistant your team is already using to write the replacement. Same engine, same limits, same refusals — there is no assistant mode with looser rules.

What an assistant may do, and what it may not
Read what the project covers and its limitsApprove a difference as acceptable
Start a run it has reviewedStart a plan it has not read
Follow progress and read the recordChange scope, policy or budget
Produce a signed evidence bundleTurn an unverified result into a pass

Deciding a difference is acceptable is a judgement about your business. A named person in your organisation makes it, sees how many comparisons it silences, and signs it with an expiry date.

Once it starts, it does not need watching. Closing a laptop does not cancel work, and a retry with the same request identifier returns the same run rather than starting a second one — so a dropped connection never costs you a duplicate database run.

Coverage catalogue

The judge, the verdicts, the rules and the signed evidence are the same for every technology. What changes is how we run each system and observe what it did. We call that a lane, and we qualify every pair of lanes before we sell it: known-good references must pass, deliberately broken conversions must be caught, and anyone must be able to replay the evidence.
