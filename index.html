The answer most tools cannot give

Three verdicts, not two

Every comparison tool returns pass or fail. That is the problem. A tool with only two answers has to pick one even when it has verified nothing — and it will pick pass, because nothing went wrong.

VerdictWhat it meansExit
equivalentBoth systems produced the same result, within the policy you approved.0
divergentThey differ. The receipt names the field and the cause.1
indeterminateWe could not verify this, and we will not pretend otherwise. Nothing comparable was produced, or the construct is outside what we can decide.2

The third verdict is the one no other tool returns, and it is the reason the first two can be trusted. An engine that never says indeterminate is not more capable. It is less honest.

Where the evidence comes from

Sign-off stops being an event at the end

Today a modernization programme verifies at milestones. Someone runs a comparison, writes a report, and a committee reads it weeks later — by which point the code has moved on and the evidence describes a system that no longer exists.

In a pipeline, every commit carries its own evidence. Sign-off becomes an accumulated record rather than a meeting, and the question at go-live changes from “can someone check this?” to “read what we already have.”

We run it on ourselves this way. Every push to our own repository runs the engine in GitHub Actions — the same command, the same exit codes, on public code you can read. It is one step in a workflow file, not an integration project.

Three ways to run it, and no difference between them. An engineer at a terminal, a step in the build you already have, or the AI assistant your team is already using to write the replacement. Same engine, same limits, same refusals — there is no assistant mode with looser rules.

What it does without asking you

It does the safe work itself. It stops before anything else.

Every verdict produces work with a named owner. Six kinds of work run unattended, because none of them can turn a difference into an acceptance: re-run the comparison, escalate to a deeper lane, extend the corpus, re-parse with a wider grammar, widen observation, and apply a normalization your team already approved.

Proposing a new normalization, classifying a change as intentional, promoting a claim — these stop and ask. Not by convention. A configuration that would let them run unattended is rejected by the software. Authority can be reduced. It cannot be increased.

Work orders

A work order is a contract, not a prompt. It declares the paths an agent may touch, the slice of the graph it may read, the gates that must pass, and the timeouts. Scope is a precondition — an agent cannot widen it at run time.

{
  "id": "intcalc-repair",
  "allowed_paths": ["src/interest/**"],
  "graph_scope": ["CBACT04C", "TCATBAL"],
  "gates": [
    { "id": "unit",    "expose_output_to_builder": true  },
    { "id": "holdout", "expose_output_to_builder": false }
  ]
}

expose_output_to_builder defaults to false and must be a real JSON boolean — a quoted "false" is rejected rather than coerced, because in Python it would evaluate as true and silently open the holdout boundary.

Verdicts and exit codes

Three verdicts, and the third is the one most tools do not have.

VerdictExitMeaning
faithful0Every compared field matched under the equivalence policy.
failed1A real divergence, classified by cause and located by field.
indeterminate2Nothing was verified. An operator error, never routed back to a builder as a defect.

The separation of 1 and 2 matters operationally. A failed run means the candidate is wrong. An indeterminate run means the harness could not tell, which is a configuration problem and must not be handed to an agent as "your code is broken."

Normalization ledger

Some differences are genuinely meaningless — a run timestamp, a padding convention. Each permitted one is a controlled entry with a written reason, a named owner, and a review date. The validator fails closed on a missing owner, an expired review, an undocumented rule, or a rule whose text no longer matches the code.

lightyr validate-normalizations --ledger spec/normalizations.json

# NORMALIZATION_REVIEW_EXPIRED:fixed-width-padding:2026-02-22
# NORMALIZATION_GOVERNANCE_MISSING:decimal-canonical:owner
# NORMALIZATION_RUNTIME_MISMATCH:copybook-filler:behavior

Prefer a shape-preserving normalization over an outright ignore. Ignoring a timestamp lets a candidate that never writes one pass; collapsing its digits still asserts format, length and punctuation.

Coverage

We measure arc coverage, not statement coverage. A corpus can execute every line of a validation paragraph and never once take the reject branch — and reject branches are where modernization defects survive to go-live.

Fidelity coverage is reported over business arcs only. Where the corpus misses one, we generate the input that reaches it — then run it through the legacy system first, because a synthetic case whose expected output a human decided is not evidence.

CI integration

The Verdict Engine is designed to be a gate, so exit codes route directly. Treat 2 as a pipeline error rather than a test failure — it means the run proved nothing.

- name: Differential verification

Questions we get asked

Frequently asked

Do you compete with code-generation platforms?

No. We sit underneath them. Generation is collapsing in price and will keep collapsing — a better model should change your throughput, not your confidence. We are the layer that decides whether generated change is safe to switch on, and we are deliberately agnostic about who wrote it. Several of our engagements verify a candidate produced by someone else's platform.

What do you need from us to start?

Read-only access to source and, for the assessment, enough captured input and output from the running system to be representative. We will tell you if it is not representative — that finding is usually the most valuable output of the first month.

Why does the product refuse to claim equivalence?

Because equivalence is a claim we make only from live evidence, and the authorised z/OS baseline is the piece still to come. The gate is enforced in code, so the moment you supply that baseline the claim unlocks. Until then the product shows you exactly where it stands.

How is this different from a golden-master test suite?

A golden master compares against outputs someone chose to capture. We measure which decision paths that capture actually reaches, then manufacture the inputs to close the gaps — usually rejection and error paths, which barely appear in production traffic and are where modernization defects survive to go-live.

Does the comparison report contain sensitive data?

Yes, by design. The expected and actual values are the evidence, and masking them would destroy the artifact. Classification, access control and retention on run directories are agreed with your security team before the first capture. This is a conversation we start early rather than discover in procurement.

What happens to the harness after the programme ends?

It stays. A modernization is a project; behavioural regression is permanent. Most customers keep the harness running against the estate long after the migration, which is when it stops being a cost line and starts being infrastructure.
